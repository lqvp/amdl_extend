## The vendor path

`_VENDOR_ROOT = Path(__file__).resolve().parents[2] / "AppleMusicDecrypt"`, derived
from this file's own location and **never** from `Path.cwd()`. The hub's CWD is
`/app` in the container and `hub/` in a dev checkout, and both are wrong, so a
CWD-derived path would work in one place and fail in the other.
`test_vendor_root_is_derived_from_this_file_not_the_working_directory` pins that
the derivation is absolute and equals `<repo root>/AppleMusicDecrypt`.

`_ensure_vendor_on_path()` inserts the root at `sys.path[0]` rather than
appending: a different `src` already on the path would otherwise win, and the
failure would look like a pydantic complaint about the wrong `Config`.

`_require_vendor_root()` checks for `<root>/src` and raises `RipperHostError`
naming the absolute path, the derivation, and the upstream project to clone. A
bare `ModuleNotFoundError: No module named 'src'` from three frames deep tells
the reader nothing.

## The config / working directory — the part worth reading

Three upstream paths are relative to the **process CWD**, and the client never
chdirs into its own tree:

1. `Config.load_from_config()` defaults to the literal `"config.toml"`, and
   `ConfigCreator.create` calls it with no argument (`src/config.py:119`).
2. `EMBEDDED_TEMPLATE_PATH = Path("assets/prefetch_template.json")`
   (`src/decrypt.py:35`) — this is what removes the wrapper `/key` round-trip
   entirely when it loads.
3. `download.dirPathFormat`, default `"downloads/{album_artist}/{album}"` —
   where files actually land.

So `start()` chdirs to the vendor root and **keeps it there** for the ripper's
lifetime; `close()` restores the previous directory.

The tempting alternative — chdir only for the duration of `start()` — provably
does not work, and the reason is worth recording because it is not obvious:

- `src/flags.py` has `language: str = it(Config).region.language` as a
  **dataclass field default**, evaluated when the class body runs.
- `src/api.py` and `src/wrapper.py` evaluate `it(Config)` and `it(GlobalLogger)`
  inside `@retry(...)` decorator arguments.

Both fire at **import** time, so `import src.rip` opens `config.toml` before a
single line of the hub's own code runs. The template and the download directory
are read at **rip** time. Import-time and rip-time need the same CWD, so it has
to persist for the host's lifetime.

`test_close_restores_the_working_directory_it_found` pins both halves: CWD is the
vendor root while started, and is the caller's original directory after `close()`.

**This is a process-global change and it is a constraint on the rest of the hub,
not a detail of this file.** While a `RipperHost` is started, no other module may
rely on a relative path. In practice that holds — every path in
`hub.config.Settings` is absolute by default and the env-supplied ones
(`AMD_LIBRARY_ROOTS`, `AMD_DB_PATH`, `AMD_WRAPPER_BASE_DIR`) are container mount
points — but it is now a documented rule, stated at the top of the seam module.

### `config_path` is a constrained argument, deliberately

`__init__` resolves the path against the caller's CWD (so a relative path is not
reinterpreted after `start()` chdirs), and `_resolve_config()` then requires it to
be the vendor's own `config.toml`, rejecting anything else.

That is a consequence, not a preference, and the error message says so.
`ConfigCreator.create` calls `load_from_config()` with its default argument, and
there is no upstream seam to pass a path through and no creart hook to override
one. The only file the client will ever read is `<CWD>/config.toml`, and the CWD
is the vendor root. Accepting a config from anywhere else would mean **silently
reading a different file than the one the caller named** — which is worse than
refusing. The message names both paths and says the file would be ignored rather
than used, because the next person would otherwise "fix" it by pointing at their
own file and get a `FileNotFoundError` from three frames inside a retry loop.

`_resolve_config` also parses the TOML and checks the five sections `Config`
requires (`region`, `instance`, `localInstance`, `download`, `metadata`), so a
config missing one fails in `start()` with a message naming the file and the
section, rather than as a pydantic `ValidationError` from inside `create()`.

## The creart order

Six creators, registered in `main.py`'s order, each import immediately followed by
its `add_creator`:

```
LoggerCreator → ConfigCreator → APICreator → WrapperCreator → DecryptorCreator → MeasurerCreator
```

The order is not a style preference, and the reason is the same import-time
`it()` mechanism described above: `src.config` must be importable *before*
`src.api` and `src.wrapper` are imported, and `src.logger` before `src.wrapper`.
Registering all six first and importing afterwards would raise a `TypeError` from
`creart._assert_supported` out of a decorator argument.

`TaskTreeCreator` is omitted. It is TUI-only, and the durable reason is that
upstream made the TUI an *optional* attachment: `src/rip.py` references
`it(TaskTree)` four times (lines 179, 633, 661, 692) and `src/mv.py` three more
(102, 171, 179), and every one of those sites is wrapped in
`try: ... except Exception: pass`. The hub is not a TUI host and renders its own
queue, so the absence of a task tree is a no-op rather than an error. The brief
pins six and the test pins the exact list.

(M6, fix round 1: my round-0 report and the `_register_creators` docstring both
said "src/rip.py never resolves it", which is wrong — it resolves `it(TaskTree)`
four times. The conclusion was right and the reason was not; both now state the
`try/except` fact, which is also why an upstream *seventh* creator would not
break the hub.)

Two things I added because the code would otherwise be wrong:

- **Registration is idempotent.** `creart.add_creator` raises `ValueError: conflict
  target` on a duplicate, so a second `start()` would turn a harmless repeat into
  a crash. Guarded by a module-level flag, since creart's creator list is a
  process-global. `test_start_twice_is_a_no_op` covers the behaviour;
  `test_registers_each_creator_only_once_per_process` covers the guard's presence.
- **A failed bootstrap is reported as fatal.** There is no way to un-register a
  creator, so a half-finished registration makes the next attempt raise
  `ValueError` on a duplicate instead of the real error. The `RipperHostError`
  says "this is fatal for the process, restart the hub to retry", so the operator
  reads the cause rather than a confusing `ValueError` on a later attempt.

`start()` then resolves all six eagerly (`it(Config)`, `it(WrapperClient)`,
`it(WebAPI)`, `it(Decryptor)`, `it(Measurer)`) and constructs `Ripper()` and
`MVRipper()`, so a config that is unreadable fails in `start()` rather than in the
first job.

## The `Leaf` → upstream translation

```python
url = Song(url=leaf.url, storefront=leaf.storefront, id=leaf.adam_id, type=URLType.Song)
await ripper.rip_song(url, leaf.codec, Flags(force_save=force, language=leaf.language))
```

`run_music_video` builds `MusicVideo(...)` with `type=URLType.MusicVideo` and calls
`MVRipper().rip(url, flags)`.

**No `parent_done` is passed, and no second re-entrancy guard was added.** Both
are deliberate and both are documented at the call site:

- `parent_done` exists purely to release a parent that is waiting on its children
  (`src/rip.py:167-170`, and the `finally` at `:290`). The hub's job scheduler
  owns parent/child bookkeeping itself; passing a handler would satisfy the wrong
  waiter and leave the hub's parent job waiting on a callback nothing calls.
- `rip_song` already returns early when `download_manager.get_task(url.id)` is
  set. A second guard would only add a second, divergent answer to the same
  question.

`run_song` **refuses a `Leaf` with `is_music_video=True`**. A music video ripped
through `rip_song` takes the FairPlay path where it needs Widevine, and fails
deep in decryption with an error naming the wrong subsystem entirely. The other
direction is not guarded, asymmetrically and on purpose: `MVRipper.rip` on a song
fails immediately and visibly on the first `/webplayback` call, which is an
acceptable report of a caller bug, whereas a silently wrong decryption path is
not.

All upstream exceptions are wrapped in `RipperHostError` with the upstream
message carried through verbatim plus the `adam_id`, and `from exc` so the
original type is in the traceback. Nothing is swallowed and nothing is replaced
with a generic string. `RipperHostError` subclasses `RuntimeError` because
`hub.config.load_settings` already raises `RuntimeError` for operator errors, and
a caller that handles one and not the other is a bug in every caller.

`wrapper_status()` returns upstream's `GET /status` payload. It calls
`cache_invalidate()` on `status` first: upstream decorates it with `@alru_cache`
and the cache never expires on its own, so a readiness gate answering from a
cached pre-death probe would report the one thing it exists to detect as healthy.
`getattr(..., "cache_invalidate", None)` is used so the seam still works if
`alru_cache` is ever replaced. A transport failure is wrapped with the wrapper
base URL in the message.

## Concerns for the next task

1. **The CWD is process-global and the hub now holds it.** Documented at the top
   of `ripper_host.py`, and every `Settings` path is absolute today. But Task 8/9
   code must not introduce a relative path anywhere, or it will resolve against
   `AppleMusicDecrypt/` while a ripper is started. This is the single most likely
   way a later task breaks something, and it fails *silently* for reads. Worth a
   line in the project AGENTS.md.
2. **`config_path` is effectively pinned to `<vendor>/config.toml`.** If the
   container ends up mounting a hub-owned config somewhere else, the seam will
   refuse it with an explanation. That is the intended behaviour (honouring it
   would mean reading a *different* file than the caller named), but it is a
   constraint the deployment has to know about before someone tries to point
   `AMD_*`-style config at a bind mount.
3. **The upstream dep block is now in `hub/pyproject.toml` and is coupled to
   upstream's pins.** An upstream bump that drops or renames a package breaks
   `uv sync` in `hub/`. That is the seam working as designed — one file's worth of
   blast radius becomes one *dependency list* worth — but it is a coupling, and it
   will need maintenance at every upgrade.
4. **`start()` is `async` but never awaits**; it is declared that way to match
   the pinned interface and to leave room for a future warm-up
   (`Decryptor.warm_prefetch`). Noted in the docstring.
5. **8 tests skip by design if the upstream runtime cannot bootstrap** — no
   `config.toml`, or a checkout that has not been `uv sync`ed. A skip is not a
   pass; the fixture says so in its own docstring. On this machine all 28 run.

## I4 — the CWD was held with nothing guarding `close()`, and a restart inherited a dead client

**In-flight guard.** A counter, not a lock: rips legitimately run concurrently
and the only question `close()` asks is whether the count is zero. Released in a
`finally`, so it releases on `BaseException` — a cancelled rip must not leave the
host permanently un-closeable, since cancelling is the normal way a shutdown
begins. `close()` now **refuses** with a `RipperHostError` naming the count and
explaining the silent-read consequence, rather than restoring the CWD under a
live rip. The docstring says the ordering is the caller's job and that Task 8/9's
shutdown path must await outstanding rips first.

Covered by `test_close_refuses_while_a_rip_is_in_flight`,
`test_close_refuses_while_a_music_video_is_in_flight` (both assert the host is
still up afterwards) and `test_a_cancelled_rip_does_not_leave_the_host_un_closeable`.

**Restart.** `close()` closing creart's process-global `WrapperClient` is a
one-way door for the process: creart's `_created` dict has no eviction, so a later
`start()` gets the same `aclose()`d instance and fails as an httpx "client has
been closed" from inside `_request`'s retry loop. `start()` now refuses, and says
to restart the hub process. The flag is **module scope**, not instance scope —
per-instance state cannot see a *different* host's `close()`, which was my first
attempt and which a direct check caught:

```
$ uv run python -c "... h1.start(); await h1.close(); await RipperHost(V).start() ..."
h1 closed. client is_closed = True
h2 start: UNEXPECTEDLY ok          <- per-instance flag, blind to h1
```

After the fix:

```
h1 closed. client is_closed = True
h2 start refused: this process already closed creart's process-global WrapperClient (via RipperHos
```

The flag is set only when the client being closed **is** the creart-resolved one
(`_global_wrapper` identity check), so a test stand-in cannot trip it, and only
on success, so a `close()` that raised does not refuse a restart that would work.

`test_start_after_close_is_refused_because_the_wrapper_client_is_gone` runs in a
**subprocess**, and that is load-bearing rather than tidy: doing it in-process
genuinely closes the shared client, and an earlier in-process version left 3 later
tests skipping with a message about a client the *test suite* had closed. A
process-terminal action belongs in its own process.

For the same reason `started_host`'s teardown detaches `host._wrapper` before
`close()` instead of calling it, and says why.

## Concerns

1. **The boundary test is a denylist, and this round is the proof of what that
   costs.** Six vectors worked; the `AppleMusicDecrypt.src` namespace-package route
   was live, needed no `sys.path` help, and would have handed the hub a second
   `Config` class. The predicate is now tested against 8 vectors *and* a symlinked
   subdirectory *and* a missing root, but a denylist is still only as complete as
   its list. The durable alternative is an allowlist (only `hub.*` and stdlib may
   be imported) or an import hook; neither was in scope here. Worth deciding
   before a fourth task adds modules.
2. **`close()` refusing on an in-flight rip is a new contract Task 8/9 must
   honour.** It is the safe default, but it means a shutdown that forgets to await
   its rips now raises instead of quietly corrupting paths. That is the intended
   trade, and it is still a change in behaviour for the caller — the shutdown path
   should be written against `close()` raising.
3. **A `RipperHost` is now strictly one-per-process.** creart's cache plus the
   one-way client close means a hub that restarts the host in-process (a config
   reload, say) must restart the process instead. `start()` says so. If a later
   task needs in-process restart, the fix belongs upstream — creart would need an
   eviction hook — not here.
4. **`force` is meaningless for music videos** and the docstring says so, but
   nothing can make a caller read a docstring. Task 8/9 should treat §7.3's
   per-file skip decision as song-only and not report a music-video skip that
   upstream will not honour.
5. **`hub/uv.lock` did not change this round** — no dependency was added, and the
   `pyproject.toml` edits were comments only. A future `uv sync` should be a no-op
   on the lock.

## Concerns

1. **The boundary predicate is now large and still a denylist.** Four checks,
   two exemption boundaries (`spike/` off `sys.path`; `builtins.`-only matching
   for the code-exec builtins), and 19 vectors. Every one of those is a decision
   someone can get wrong, and this round showed the failure mode is *silent
   narrowing* — the spike exemption was a reasonable-looking simplification that
   reopened the exact vector the rule existed for. The invariant that would remove
   the class of bug is an allowlist (only `hub.*` and stdlib importable) or a real
   import hook. That is a design change, not a fix round, and it should be a
   deliberate decision rather than a third patch.
2. **`spike/` has one unenforced vector by design.** A `sys.path` mutation in a
   spike script pointing at the vendor tree would not be caught. `spike/` is not
   packaged and its scripts point at the hub, so the exposure is a dev scratch
   file rather than shipped code — but it is a hole, it is deliberate, and
   `test_the_spike_exemption_is_only_sys_path` documents exactly how narrow it is.
3. **One host per process is now enforced, so an in-process config reload cannot
   work.** Task 8/9 must not build a second `RipperHost` to pick up new settings;
   it has to restart the process. This is stricter than round 1 and is the correct
   reading of a process-global CWD, but it is a contract change.
4. **Three of the 66 tests are now subprocess tests**, which is slower (3.8 s vs
   3.2 s) and means a failure in one surfaces as text in `pytest`'s captured
   stdout rather than as a traceback. That is a real diagnostic regression; the
   text is asserted on explicitly to compensate, but a genuine crash inside those
   snippets would need `capsys`-style inspection to localise.
